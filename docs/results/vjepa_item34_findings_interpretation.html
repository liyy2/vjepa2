What GPT's experiments actually mean

Plain-English interpretation of vjepa_item34_findings_summary.html. The summary mixes four different approaches in one table without saying which one is which — here's a sorted version.

The one sentence

V-JEPA went from QWK 0.47 to 0.69 honestly, and 0.83 when fused with the kinematic baseline (optimistic) — but the head you and I designed (variable-K + learned aggregator) was not what got it there. The win came from caching V-JEPA embeddings, computing hand-crafted statistics over them, and training a gradient-boosted stacker on those — basically applying the kinematic-baseline recipe to V-JEPA features instead of MediaPipe keypoints.

Two approaches were tried, only one worked

Approach A — what we asked for: variable-K windows + learned aggregator head

This is the direct realization of the design discussion: K_i = ceil(duration_s) windows, mask-aware head, train end-to-end. Three head choices × three encoder regimes (frozen, supervised-LoRA, etc.).

None of the 6 variants beat the fixed-K=4 baseline (QWK 0.465). Several collapsed to class prior — i.e. the model gave up and predicted the majority class for everyone. So the "give V-JEPA more windows + learn how to aggregate" theory, in its direct form, failed.

Why this failed. ~200 training clips is too few to learn an aggregator on top of variable-length attention-pooled sequences end-to-end. The head has nowhere to anchor itself — every clip is a different sequence length, the supervised signal is one ordinal label per video, and the aggregator has no inductive bias for "find the finger-tap rhythm." With six possible severity-class outputs and ~40 train examples per class, gradient descent finds the class-prior solution and stays there.

Approach B — the one that worked: cache embeddings → hand-crafted stats → tabular stacker

Instead of training the aggregator with gradients, GPT cached per-window V-JEPA embeddings to disk, computed hand-crafted statistics over them (mean / std / percentiles across windows), then trained a LightGBM-style stacker on those features. Same recipe the kinematic baseline uses — applied to V-JEPA features.

The 0.829 fused number is the most-cited and the most-misleading. It is validation-tuned — the fusion weight was picked using the val set itself, so it's an upper bound on what fusion could do, not what it will do on a held-out fold. The honest read is: V-JEPA-only is still well behind kin, but adds enough complementary signal that a calibrated fusion should push past kin alone. The number to chase is "fit fusion weights on subject-level out-of-fold train predictions, evaluate once on val" — which hasn't been done yet (it's GPT's next-step #1).

What "subject-OOF" means and why it dropped the V-JEPA numbers

Earlier V-JEPA-only stacker numbers were quoted around QWK 0.73. The honest re-run lands at 0.67–0.69. The difference is a CV leakage fix:

  • Old inner CV: randomly split clips across inner folds. Same patient could have a left-hand clip in train and a right-hand clip in holdout. The model gets to memorize patient-specific features.
  • New inner CV: split by subject. All clips from one patient go into the same fold. This matches how the outer 5-fold split works and is the only honest readout. About 4 QWK points of the earlier improvement was leakage.
Trust only the subject-OOF rows. Anything labeled "val-selected," "val-tuned," or "train-fitted" tuned its hyperparameters or fusion weights on the val set you're reporting on. Those numbers exist to show that complementary signal is there, not to claim performance.

So why didn't the variable-K + learned aggregator work?

This is the part of the summary that buried the lede. Two real reasons:

  1. The hypothesis ("V-JEPA fails because of coverage") was only partly right. Coverage does correlate with error — we confirmed this on the original baseline. But fixing coverage doesn't automatically fix accuracy, because the bottleneck wasn't just "did the model see enough seconds" but also "can the model extract tap-rate / amplitude / decrement from those seconds at all." V-JEPA's frozen attentive features encode what the hand looks like; they don't natively encode what the hand is doing rhythmically. More frames of the same uninformative embedding don't help.
  2. The successful recipe explains what V-JEPA actually contributes. The cached-stats stacker works because mean / percentiles / std over the per-window embedding sequence summarize change over time — i.e. the part of the signal the static representations were missing. That's exactly the same thing the kinematic baseline does with MediaPipe keypoints, just at a higher level of abstraction. The learned aggregators failed to discover this because they had to learn the same idea from scratch with 200 examples.

What I'd do next, in priority order

  1. Honest fusion (GPT's #1, do this first). Refit the kin + cached-V-JEPA fusion weights using subject-OOF train predictions, then score once on val. If it stays above kin-alone, you have a real result; if it collapses to kin-alone weight, the 0.829 was the val-tuning artifact. Cheap; no GPU.
  2. Five-fold CV. 66 val clips is too few. 0.689 vs 0.465 is a real gap but the noise floor at this N is large. Run the cached-stacker recipe on folds 1–4 to confirm the win is fold-stable, not a one-fold artifact.
  3. Drop the direct adaptive-head approach. The collapsed-to-prior rows are a signal that this branch is not going to bridge the gap at N≈200. The cached pathway is the path forward for V-JEPA-only.
  4. If V-JEPA-only matters: motion-biased inputs. The reason kinematic wins is that it works on extracted velocity / amplitude / frequency signals. To make V-JEPA competitive on its own, the model has to ingest something equivalent — either RGB frame differences, optical flow channels, or a temporal-contrastive pretext loss that biases the features toward motion. This is a real research project, not a config tweak.
  5. For the publication / clinical metric: stop tracking accuracy, track QWK. The cached stacker drops 3 percentage points of accuracy while gaining 22 points of QWK. For an ordinal severity score, that's the right direction; flat accuracy hides it.

Implementation honesty check

The summary lists a bunch of new files in the worktree. The ones that actually contributed to the honest 0.689 result are:

  • scripts/pd_hand/temporal_oof_stacker.py — the cached-stats stacker with subject-grouped inner CV. This is the working pipeline.
  • The cached NPZ embeddings on disk that the stacker reads from.

The files that produced the failed adaptive-head numbers are:

  • src/datasets/clip_dataset.py (adaptive windows + mask)
  • src/heads/adaptive_stats_head.py
  • src/heads/xception_time_head.py
  • src/heads/temporal_agg_head.py (mask support)
  • src/heads/window_mil_corn_head.py

These are still useful — the adaptive sampler is the right plumbing for any future V-JEPA recipe that does use full clip coverage. But none of them is currently on the path to the best V-JEPA-only result. Keep them, don't rely on them.

Bottom line. GPT did the right experiments; the writeup just doesn't separate the "experiment we proposed and ran" (failed) from the "experiment that worked anyway" (cached stats stacker). The honest V-JEPA-only number on this fold is QWK 0.689, up from 0.465. Kin is still ahead at 0.818. The honest fusion experiment hasn't been done yet — that's the next concrete thing worth running.
